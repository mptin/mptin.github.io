    ЛР 9. Работа с графикой. SourceCraft. CI/CD. Артефакты¶

    Цель работы¶

    Освоить анализ и визуализацию данных через pandas и matplotlib, а также автоматическое выполнение Jupyter-ноутбука в CI с публикацией результатов как артефактов сборки.

    Задание¶

    1. Сделать форк репозитория shaliko9/itmo-python-lab-template.
    2. Выполнить задание из ipynb-файла, заполнить пропуски.
    3. Выполнить самостоятельную работу.
    4. Дополнить CI так, чтобы раннер дописывал в первую или последнюю ячейку текст, подтверждающий, что код выполнен именно раннером, а не локально и не в Google Colaboratory.

    CI по требованиям шаблона запускается автоматически, устанавливает зависимости, выполняет notebook, генерирует отчёт и сохраняет его как артефакт в формате HTML.

    Репозиторий на SourceCraft: https://sourcecraft.dev/anthony-004/itmo-python-lab-template

    Пайплайн lab-check отработал на коммите 7464f2 за 2 мин 1 сек, все пять шагов успешны. В артефактах executed_lab.ipynb и report.html; в отчёте сошлись все четыре проверки происхождения запуска — переменные раннера (40 шт.), Linux, контейнер и отсутствие Colab. Хост раннера worker-group-1-ru-central1-a, Python 3.11.16.

    Реализация¶

    Данные¶

    StudentsPerformance.csv, результаты 1000 студентов по трём предметам (математика, чтение, письмо) и пять категориальных признаков: пол, этническая группа, образование родителей, тип обеда, прохождение подготовительного курса. Пропусков и дубликатов нет.

    Структура репозитория¶

    .
├── data/StudentsPerformance.csv
├── lab.ipynb              # notebook с выполненной работой
├── ci_signature.py        # отметка раннера о выполнении (пункт 4 задания)
├── requirements.txt
└── .sourcecraft/ci.yaml   # конфигурация CI/CD pipeline

    executed_lab.ipynb и report.html в репозитории не лежат: их создаёт пайплайн, и скачивать их надо со страницы запуска. Держать в репозитории копию, собранную локально, бессмысленно и вводит в заблуждение.

    Что сделано в ноутбуке¶

    Загрузка данных, первичный анализ, проверка пропусков, переименование столбцов, создание трёх новых признаков (average_score, score_range, grade), описательная статистика, группировка по четырём категориальным признакам и пять графиков, каждый с заголовком, подписями осей и текстовым выводом.

    Конфигурация CI¶

    on:
  push:
    - workflows: [lab-check]
      filter:
        branches: ["main", "master"]
  pull_request:
    - workflows: [lab-check]

workflows:
  lab-check:
    tasks:
      - name: run-notebook-and-build-report
        cubes:
          - name: execute-notebook
            image: docker.io/library/python:3.11
            script:
              - pip install --no-cache-dir -r requirements.txt
              - jupyter nbconvert --to notebook --execute
                  --ExecutePreprocessor.timeout=600
                  --output executed_lab.ipynb lab.ipynb
              - python ci_signature.py executed_lab.ipynb
              - jupyter nbconvert --to html --output report.html executed_lab.ipynb
              - ls -lh executed_lab.ipynb report.html
            artifacts:
              paths:
                - executed_lab.ipynb
                - report.html

    Отметка раннера¶

    Это самая содержательная часть задания. Первая версия скрипта просто искала переменные окружения с префиксами CI_, SOURCECRAFT_ и подобными, и если хоть одна находилась, писала «выполнено раннером».

    Такую отметку легко подделать. Достаточно запустить локально CI_COMMIT_SHA=... python ci_signature.py, и ноутбук начнёт утверждать, что собран в CI, при этом в соседней строке той же таблицы будет стоять имя моего ноутбука и путь /Users/.... Доказательство, которое опровергает само себя, хуже, чем никакого.

    Поэтому проверок стало четыре, и вывод «выполнено раннером» делается, только если сходятся все:

    Проверка Как проверяется
    Переменные окружения раннера есть переменные с известными префиксами
    Операционная система Linux platform.system() == "Linux"
    Запуск в контейнере существует /.dockerenv либо docker/containerd/kubepods в /proc/1/cgroup
    Не Google Colab не задана COLAB_RELEASE_TAG и нет каталога /content 
    def looks_like_container() -> bool:
    """Проверить, выполняется ли код внутри контейнера."""
    if Path("/.dockerenv").exists():
        return True

    try:
        cgroup = Path("/proc/1/cgroup").read_text(encoding="utf-8")
    except OSError:
        return False

    return any(name in cgroup for name in ("docker", "containerd", "kubepods"))

    В отметку попадает таблица со всеми четырьмя проверками и тем, что по каждой нашлось. Если сошлись не все, заголовок меняется на «локальный запуск», и текст прямо перечисляет, чего не хватило.

    Результаты¶

    Пайплайн выполняет ноутбук без ошибок и публикует два артефакта: executed_lab.ipynb и report.html с пятью графиками и отметкой раннера в конце.

    Тип обеда (стандартный против льготного) 8.6

    Подводные камни¶

    Порядок шагов в CI критичен

    Отметка добавляется после nbconvert --execute. Если поменять шаги местами, nbconvert перезапишет файл результатом выполнения, и отметка бесследно исчезнет. HTML собирается последним, уже из подписанного ноутбука, иначе отметка попадёт в .ipynb, но не в отчёт.

    Здесь нельзя использовать бэкенд Agg

    В ЛР 2 графики сохранялись в файлы, и для этого нужен matplotlib.use("Agg"). В этой работе так делать нельзя: при Agg картинки не попадают в вывод ячейки, и HTML-отчёт из CI окажется без графиков. Нужен %matplotlib inline, он работает и без графического окружения, поэтому в контейнере всё строится нормально.

    Повторный запуск не плодит отметки

    Предыдущая находится по скрытому маркеру <!-- ci-signature --> и заменяется новой.

    Переменные CI собираются по префиксам, а не по именам

    Список строится по CI_, SOURCECRAFT_, SC_, JOB_, RUNNER_ и другим. Так отметка не сломается, если платформа переименует переменные или добавит новые.

    --ExecutePreprocessor.timeout обязателен

    По умолчанию у nbconvert небольшой лимит времени на ячейку. Долгая ячейка роняет сборку с CellTimeoutError при полностью рабочем коде.

    Ноль баллов по математике не ошибка данных

    Минимум по математике равен 0, и сначала это выглядит как брак. Проверка строки целиком показала, что у того же студента 17 и 10 баллов по другим предметам: результат согласованный, удалять его нельзя.

    Выводы¶

    Артефакты нужны, чтобы вынести результат работы CI наружу. Всё, что создано внутри контейнера сборки и не объявлено артефактом, исчезает вместе с контейнером.

    Главный урок работы оказался про само доказательство. Отметка, которая опирается только на переменные окружения, ничего не доказывает, потому что переменные выставляются одной строкой в терминале. Признаки надо брать такие, которые на локальной машине воспроизвести нельзя: контейнер, ядро Linux, отсутствие домашнего каталога пользователя. И отметка обязана честно говорить «локальный запуск», когда проверки не сошлись.

    Выполнение ноутбуков в CI делает результаты воспроизводимыми. Ноутбук, выполненный вручную, отражает состояние конкретной машины со своим набором версий библиотек, а в CI он собирается с нуля в чистом контейнере.

    Отдельно про усреднение. Итоговая разница по полу в 3.7 балла выглядит незначительной, хотя за ней стоят расхождения в 5-9 баллов в разные стороны. Прежде чем делать вывод по агрегированной величине, стоит посмотреть на её составляющие.
