## Задание

Сделать сервис, который подсказывает сотруднику банка, стоит ли одобрять
ипотеку. Требования:

* обработать данные: очистка, кодирование категорий, масштабирование, разбиение
  на train/test, отбор признаков;
* обучить и сравнить минимум две модели, выбрать лучшую по ROC-AUC, сохранить
  её в файл;
* сделать API на FastAPI с тремя методами: `/upload-model`, `/predict`,
  `/predict-from-csv`;
* сделать простой интерфейс (вайбкодинг разрешён, но нужно приложить промпты);
* писать код по DAST/DATS: тесты, аннотации типов, докстринги, PEP-8;
* настроить CI на SourceCraft с тестами и линтингом фронтенда и бэкенда;
* зависимости вести через менеджер `uv`.

## Что получилось

Веб-приложение, которое:

* принимает данные клиента через форму и сразу показывает решение и
  вероятность одобрения;
* умеет обрабатывать целый csv-файл и считать по нему качество модели;
* позволяет загрузить новую модель, не перезапуская сервис.

## Часть 1. Данные и модель (Солдатов Павел)

### Что в данных

Датасет `loan_data.csv`: 45 000 заявок, 13 признаков, целевая переменная
`loan_status` (1 — одобрено, 0 — отказ). Одобрено 22.2% заявок, то есть классы
несбалансированы: отказов почти вчетверо больше.

Пустых значений и дубликатов нет. Зато нашлись явные опечатки при вводе:

| Признак | Максимум в данных | Что сделали |
|---|---|---|
| `person_age` | 144 года | удалили строки, где больше 100 |
| `person_emp_exp` | 125 лет стажа | удалили строки, где больше 60 |

Строки удалили целиком, а не заменили значения границей диапазона: возраста
144 года не бывает, это ошибка ввода. Удалено 10 строк из 45 000, то есть 0.02%
данных.

### Как подготовили признаки

Текстовые признаки (например, цель кредита) модель понимать не умеет, ей нужны
числа. Поэтому:

* `OneHotEncoder` превращает каждую категорию в отдельный столбец из нулей и
  единиц;
* `StandardScaler` приводит числа к одному размаху, чтобы доход не перевешивал
  кредитный рейтинг просто потому, что числа крупнее.

Всё это собрано в один объект `Pipeline`, внутри которого лежит и обработка
данных, и сама модель.

Данные разбили на обучающую и тестовую части в пропорции 80/20 с параметром
`stratify`. Он следит, чтобы доля одобренных заявок в обеих частях была
одинаковой. При несбалансированных классах без этого тестовая выборка может
случайно получиться непохожей на обучающую.

### Отбор признаков

Проверяли так: берём один признак, случайно перемешиваем его значения по всем
строкам и смотрим, насколько просело качество модели. Если просело сильно —
признак важный. Если не просело — модель им и не пользовалась. Метод называется
permutation importance, считали его на тестовой выборке.

| Признак | Важность |
|---|---|
| previous_loan_defaults_on_file | 0.2956 |
| loan_percent_income | 0.0380 |
| loan_int_rate | 0.0348 |
| person_income | 0.0271 |
| person_home_ownership | 0.0266 |
| loan_intent | 0.0111 |
| credit_score | 0.0042 |
| loan_amnt | 0.0010 |
| person_age | 0.0007 |
| person_education / person_emp_exp / person_gender | 0.0000 |
| cb_person_cred_hist_length | −0.0001 |

Оставили 7 признаков из 13. Качество при этом практически не изменилось:

| Набор признаков | ROC-AUC |
|---|---|
| все 13 | 0.9768 |
| отобранные 7 | 0.9767 |

Разница в четвёртом знаке, то есть её фактически нет. Зато сервису нужно почти
вдвое меньше полей: форма короче, и ошибиться при вводе сложнее.

### Сравнение моделей

Обучили три модели на одних и тех же данных.

| Модель | ROC-AUC (13 признаков) | ROC-AUC (7 признаков) |
|---|---|---|
| **Градиентный бустинг** (HistGradientBoosting) | **0.9768** | **0.9767** |
| Случайный лес | 0.9743 | 0.9725 |
| Логистическая регрессия | 0.9540 | 0.9518 |

Выбрали градиентный бустинг. Подробнее по нему:

```
              precision    recall  f1-score   support
       отказ       0.94      0.97      0.96      6998
    одобрено       0.88      0.79      0.84      2000
    accuracy                           0.93      8998
```

Читается так: из всех заявок, которые модель назвала одобренными, реально
одобрены 88%. А из всех реально одобренных модель нашла 79%.

### Откуда такое высокое качество

ROC-AUC 0.977 для кредитного скоринга очень много. Объяснение нашлось в данных.

Признак `previous_loan_defaults_on_file` («были ли раньше просрочки») решает
почти всё. Если посмотреть на данные напрямую:

* если раньше был дефолт — отказ в 100% случаев, 22 858 строк, ни одного
  исключения;
* если дефолта не было — одобряют 45.2% заявок.

То есть в датасет зашито жёсткое правило: был дефолт — отказ всегда. Одного
этого признака хватает, чтобы получить ROC-AUC 0.83 вообще без обучения модели.

Утечкой данных это назвать нельзя: о прошлых просрочках банк знает до решения, и
использовать их законно. Но модель во многом просто повторяет готовое правило
вместо того, чтобы находить закономерности. Риск в том, что если это поле начнёт
приходить пустым или недостоверным, качество резко упадёт.

### Что сохраняется в файл модели

В файл идёт весь `Pipeline` целиком и служебная информация: список признаков,
название алгоритма, ROC-AUC, дата обучения.

Если сохранить только модель, а кодирование и масштабирование выполнять на
сервере вручную, рано или поздно обработка на сервере разойдётся с обработкой
при обучении. Сервис при этом не упадёт: он продолжит отвечать, просто ответы
станут неверными.

## Часть 2. Бэкенд (Ашихмин Кирилл)

### Методы API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/upload-model` | загрузить файл модели в формате pkl |
| POST | `/predict` | предсказание по одной или нескольким заявкам |
| POST | `/predict-from-csv` | предсказание по csv-файлу, с расчётом ROC-AUC |
| GET | `/model-info` | какая модель сейчас загружена |
| GET | `/health` | сервис жив, модель загружена или нет |
| GET | `/` | веб-интерфейс |

Первые три требовались заданием, остальные добавлены для удобства: интерфейсу
нужно знать, загружена ли модель, и какие поля она ожидает.

### Что возвращает `/predict`

Принимает список заявок, возвращает по каждой исходные признаки плюс решение:

```json
{"predictions": [{
  "person_income": 71948.0, "loan_int_rate": 16.02,
  "loan_percent_income": 0.49, "credit_score": 561,
  "person_home_ownership": "RENT", "loan_intent": "PERSONAL",
  "previous_loan_defaults_on_file": "No",
  "loan_status": 1, "decision": "одобрено", "approval_probability": 0.998
}]}
```

Кроме метки возвращается вероятность. Порог 0.5 задаёт банк, сотрудник видит
вероятность и решает сам. Поменять порог можно без переобучения модели.

### Что возвращает `/predict-from-csv`

Принимает csv и работает с двумя вариантами файла: и с «сырым» со всеми
исходными столбцами (например, полученным из `train_test_split`), и с уже
подготовленным, где только отобранные 7 признаков.

Возвращает весь датасет со столбцом `predicted_loan_status`. Если в файле был
столбец `loan_status` с правильными ответами, сервис дополнительно считает
ROC-AUC.

### Как загружается модель

Модель читается с диска один раз при старте и лежит в памяти в объекте
`ModelStore`. Если читать файл на каждый запрос, сервис станет очень медленным.

Когда файла модели нет, сервис всё равно запускается и пишет предупреждение в
лог. Модель потом можно дослать через `/upload-model`. Так сервис не падает при
развёртывании, если модель ещё не обучена.

### Обработка ошибок

Сервис должен ломаться предсказуемо и объяснять, что не так.

| Ситуация | Ответ |
|---|---|
| модель не загружена | 503 и текст «отправьте pkl на /upload-model» |
| загружен битый файл или не модель | 400 с причиной |
| в csv нет нужных столбцов | 400 со списком недостающих |
| значение поля вне допустимого диапазона | 422 с указанием поля |
| в csv все строки одного класса | ROC-AUC не считается, возвращается `null` |

Последний случай особый: ROC-AUC математически не определён, если в данных
только один класс. Сервис из-за этого не падает и возвращает `null`.

### Проверка входных данных

Проверки описаны в `app/schemas.py` через библиотеку `pydantic` и срабатывают
до того, как данные дойдут до модели.

| Поле | Ограничение |
|---|---|
| `person_income` | больше 0 |
| `loan_int_rate` | от 0 до 100 |
| `loan_percent_income` | от 0 до 1 |
| `credit_score` | от 300 до 850 |
| `person_home_ownership` | RENT / OWN / MORTGAGE / OTHER |
| `loan_intent` | один из 6 вариантов |
| `previous_loan_defaults_on_file` | Yes / No |

Если прислать `credit_score: 9999`, сервис ответит 422 и скажет, какое поле не
подходит, вместо того чтобы отдать модели бессмысленное число.

## Часть 3. Интерфейс (Ашихмин Кирилл)

Страница сгенерирована с помощью LLM. Задание это прямо разрешает при условии,
что промпты приложены.

`app/static/index.html` — одна HTML-страница без фреймворков и сборщиков. Три
блока: форма с данными клиента, статус модели с возможностью загрузить новый
pkl, загрузка csv-файла.

Оформление сделано в стиле печатного отчёта: шрифт с засечками, разделы
пронумерованы римскими цифрами, тонкие линейки вместо карточек с тенями. Цвет
почти не используется, только тёмно-зелёный и тёмно-красный узкой полосой рядом
с решением. В том же стиле оформлена и страница документации API.

??? note "Полный текст промпта, по которому сделана страница"

    Свёрстай одну статическую HTML-страницу без внешних зависимостей и
    сборщиков для сервиса предсказания одобрения ипотеки.

    Содержание. Три раздела: (1) форма из 7 полей — `person_income`,
    `loan_int_rate`, `loan_percent_income`, `credit_score` числовыми полями,
    `person_home_ownership`, `loan_intent`, `previous_loan_defaults_on_file`
    выпадающими списками с русскими подписями; по кнопке шлёт
    `POST /predict` с телом `{"records":[{...}]}` и показывает решение,
    вероятность и индикатор заполнения; (2) статус модели — читает
    `GET /health` и `GET /model-info`, плюс форма загрузки `.pkl` на
    `POST /upload-model`; (3) форма загрузки `.csv` на `POST /predict-from-csv`,
    показывает число обработанных строк, ROC-AUC и первые 5 строк ответа.

    Оформление академическое, как у печатного отчёта. Шрифт с засечками для
    заголовков и текста, моноширинный для числовых значений, мелкий
    прописной с разрядкой для подписей полей. Разделы пронумерованы римскими
    цифрами. Вместо карточек с тенями и скруглениями — тонкие линейки и
    прямые углы. Шапка как титульный лист: название, строка с номером работы и
    автором, двойная линейка под ней. Цвета почти нет: тёмные чернила на
    бумажном фоне, тёмно-зелёный для одобрения и тёмно-красный для отказа,
    только как узкая полоса слева от блока с решением.

    Ошибки API показывать пользователю текстом, а не в консоли. Вёрстка
    адаптивная, в одну колонку на экранах уже 480 пикселей. Без анимаций.

!!! note "Почему тесты и обучение в одном шаге"

    Тестам API нужен файл модели, а в репозитории его нет: это бинарный
    артефакт сборки, он лежит в `.gitignore`. Поэтому сначала выполняется
    обучение, потом тесты.

    Разнести их по разным шагам нельзя: у каждого шага своя файловая система, и
    модель, обученная в соседнем шаге, будет не видна.

## Что оказалось неочевидным

!!! danger "Пустое поле чуть не начало терять заявки"

    Очистка данных сначала оставляла строки по условию `person_age <= 100`.
    Если возраст не указан вообще, такое сравнение даёт «ложь», и строка
    удалялась вместе с настоящими опечатками.

    При этом `person_age` в модель вообще не входит, его отсеял отбор
    признаков. Клиент загружал csv на 100 строк, получал 98 и не понимал, куда
    делись две, а сервис не показывал ни ошибки, ни предупреждения.

    Условие переписали на `~(person_age > 100)`. Теперь удаляются только
    физически невозможные значения, а строки с пустым возрастом остаются:
    пустое поле означает «не знаем». На этот случай написан отдельный тест.

    Заметить это удалось только когда специально подсунули файл с пустым полем
    и сравнили число строк на входе и на выходе.

!!! warning "Модель держится на одном признаке"

    Важность `previous_loan_defaults_on_file` на порядок выше всех остальных
    вместе взятых. С точки зрения банка это логично, прошлые просрочки лучше
    всего предсказывают будущие. Но сервис из-за этого уязвим: испортится одно
    поле, и качество обвалится.

!!! note "Пол в модель не попал"

    У признака `person_gender` важность ровно 0.0000, технически он не нужен.
    Удачно получилось и с правовой стороны: принимать кредитные решения на
    основании пола во многих странах запрещено, и модель с таким признаком не
    прошла бы проверку регулятора.

!!! note "Неизвестная категория не должна ронять сервис"

    Если в запросе придёт категория, которой не было при обучении,
    `OneHotEncoder` по умолчанию выбрасывает исключение. Поэтому он настроен с
    параметром `handle_unknown="ignore"`: такой объект просто получит нули по
    этому признаку, а сервис ответит нормально.

!!! note "Настройки flake8 не читаются из pyproject.toml"

    Сначала настройки линтера положили в `pyproject.toml`, в секцию
    `[tool.flake8]`. Оказалось, что flake8 этот файл не читает, и секция просто
    ничего не делала. Локально линтер ругался на длину строк, а CI проходил,
    потому что там лимит передавался флагом. Настройки перенесли в отдельный
    файл `.flake8`, и теперь локальная проверка и CI проверяют одно и то же.
